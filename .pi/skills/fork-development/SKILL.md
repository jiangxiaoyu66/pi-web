# Fork 扩展开发

面向：让 AI 执行调研与开发、自己审批方案和提交的仓库维护者。中文输出，先总后分，重点讲结论、难点和兼容风险。Skill 是操作规范，不是权限隔离机制。

## 原则与授权

- 官方配置或扩展能较好满足需求，就不改官方源码。先证明具体限制，再考虑独立模块及最小核心接入；不为方便而绕过扩展。
- 方案确认前只读调研，不修改业务代码、安装依赖、创建分支或发布 GitHub 内容。用户要求“先看看”时止步于调研。
- 方案批准只授权该范围内的实现。提交前展示成果并等待明确确认；Commit、Push、创建 PR、合并分别按用户授权执行，不相互默认授权。
- 不顺手重构或全仓格式化，不删除/跳过测试以求通过，不强推，不覆盖用户改动。重要范围变化重新确认。

## 流程

1. 确认目标仓库、上游和需求。只读检查工作区、remote、分支、项目规则及相关实现。优先读取已有定制清单与基线；不假设 main 一定是官方基线。
2. 查官方文档、配置和扩展 API，按需求给出可满足与不可满足部分，并引用版本/源码位置。若涉及 Pi harness，读取对应本地官方文档和示例后再设计。
3. 查上游 open/closed Issue、PR；有 Discussions 时按需查。使用需求同义词、实现术语和可能的编辑器/平台名称。GitHub 可用 `gh issue list --repo OWNER/REPO --state all --search '关键词'`、`gh pr list`，再用 `gh issue view NUMBER --repo OWNER/REPO --comments` / `gh pr view` 阅读相关正文及评论。记录查询时间、链接、创建/更新时间、状态、作者或维护者回复、关联 PR、合并与发布情况。搜索失败明确覆盖限制；不能把零命中说成确定不存在。
4. 按下表给出建议，并提交短方案，等待用户确认。只做可行性咨询时不进入实现。
5. 获准后从实际自用分支建立独立需求分支，按小步实现并执行相关测试/构建；UI 变更需按可用条件进行真实浏览器验证。保留扩展与官方接入点的边界，无法验证如实说明。
6. 更新已有定制清单（不存在时用 `docs/customizations.md`）：每项记录目的、为何不能只用官方扩展、接入位置、对应测试、关联上游链接及可删除条件。不创建重复记录体系。
7. 交付验收摘要及关键 diff，等待提交授权。不得声称未运行的测试已通过。

## 上游决策

| 证据 | 行为 |
| --- | --- |
| 官方配置/扩展足够 | 用官方机制，不改核心；必要配置也先获准 |
| 已合并且当前版本可用 | 优先复用；若需升级，转 fork-upgrade，不擅自升级 |
| 已合并未发布、PR 正在评审或维护者明确在做 | 说明时间、范围与不确定性，建议等待或最小临时方案，由用户决定 |
| 只有 Issue、社区提案或久无实质进展 | 不声称官方正在做；比较等待成本与最小实现成本 |
| 无充分证据或需求仅部分重合 | 明确未知和差异，不编造排期，也不以最近更新时间代表开发进度 |

## 输出契约

方案保持总分结构，一般不超过以下五项；小需求每项一句：

- **结论**：复用官方 / 等待 / 自己实现，以及理由。
- **依据**：相关源码与 Issue/PR 链接、日期、处理状态；事实与推断分开。
- **改动与难点**：复用什么、新增什么、最少触及哪里及关键取舍。
- **兼容与验收**：官方接入点、升级风险、验证方法。
- **待确认**：明确本次申请授权的范围；未确认停止。

提交前摘要：做了什么、怎么体验、关键文件与差异、已执行检查及结果、未验证项/风险、建议提交内容。若建议先升级，向 fork-upgrade 交接目标仓库、当前基线、候选上游提交/版本及证据，仍需该流程的升级确认。
