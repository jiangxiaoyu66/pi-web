# Fork 官方更新

面向：让 AI 负责更新适配、自己审批升级和提交的 Fork 维护者。中文、总分结构，挑重点和难点。Skill 不是强制权限系统。

## 边界

- “检查更新”只授权获取上游元数据、fetch 及不修改工作区的比较，不授权 merge/rebase、安装依赖、执行不可信代码、改工作区文件、Commit、Push 或合并 PR。fetch 会写入 Git 元数据；用户明确要求严格只读时，不执行 fetch，改用远端 API 与已有本地数据，并说明比较局限。
- 升级方案通过后才创建分支和实施；提交前再次确认。Commit、Push、PR、合入稳定分支分别依授权执行。
- 不自动定时更新、不追逐每次提交；不得擅自切换运行中的服务或修改全局安装。本流程只处理仓库更新，运行环境切换另行授权。
- 不 reset --hard、不 clean、不强推、不自动 stash 用户改动。存在未提交改动，报告并停止会影响工作区的操作，或经许可使用独立 worktree。

## 流程

1. 检查项目规则、工作区、remote、分支、定制清单、当前官方基线与验证命令。通过 remote 和 GitHub Fork 关系核实上游，不把 origin 当官方，不把本地 main 当已同步的事实。
2. 记录查询时间，fetch 已确认的上游，读取发布说明、关键提交及相关 Issue/PR。明确区分最新提交、最新发布版、当前基线；选一个明确的候选目标 SHA/标签，避免实施中目标漂移。基线不明时用历史和 merge-base 辅助推断，说明置信度，不伪造“当前基于某版本”。
3. 比较目标与自用分支，评估每个自定义功能：扩展 API、核心接入、依赖、数据格式、配置和行为是否变化。区分原有失败与升级新增失败。没有文本冲突也必须检查行为兼容。
4. 检查官方是否已经覆盖自定义需求，阅读关联 Issue/PR 的正文、评论、时间和发布状态。仅提出删除/迁移补丁建议，不擅自删除；PR 合并不等于已发布或当前可用。
5. 输出下方短方案，等待明确升级授权。若只是查看更新，到此结束。
6. 获准后记录升级前自用 HEAD、官方旧基线和目标 SHA，确保可找回；从自用稳定分支建立 `sync/<标识>`。通常 merge 已确认的目标，不对已共享自用历史反复 rebase。不存在约定分支时先确认分支策略，不自行改名或重建 main。
7. 解决冲突并检查语义变化；若必须扩大改动、删除功能或改变数据兼容策略，重新确认。检查官方改动附带的脚本，依项目规则执行验证，不盲目运行外部代码。
8. 执行已有测试、构建和每项定制回归；涉及 UI 时按条件做真实浏览器验证。未能运行或失败的检查如实记录，不降标准。更新已有基线/定制清单；没有记录时只建立必要的最小文档。
9. 展示验收报告和 diff，等待提交授权。提交后也不自动 Push 或合入。失败时保留诊断信息，稳定分支不动；撤销独立分支/worktree 前确认用户新增改动。已经共享的提交用 revert 或另行确认的恢复方案，不强推改写。

## 升级判断

| 情况 | 建议 |
| --- | --- |
| 必要安全修复、所需功能且兼容风险可控 | 推荐升级，列明依据 |
| 有价值但破坏扩展/API 或迁移成本高 | 说明收益、适配难点和验证缺口，等用户决定 |
| 收益小且变动大/验证不足 | 建议暂缓，不因存在更新就升级 |
| 官方已提供等价能力 | 提议删除补丁或迁移到官方扩展，单独列明范围并获准 |

## 输出契约

检查/方案一般用五项，每项只写必要信息：

- **结论**：建议升级 / 暂缓，以及主要理由。
- **目标与收益**：旧基线、候选 SHA/版本、关键变化及真实链接/日期。
- **难点与兼容**：受影响定制、冲突和行为风险，事实与预测分开。
- **实施与验收**：升级分支、必要适配、验证方法及升级前恢复点。
- **待确认**：明确授权范围；未确认不实施。

提交前报告：目标 SHA、实际关键差异、逐项验证结果、未验证项、残余风险、恢复点和建议提交内容。交接记录应可供 fork-development 继续读取：当前官方基线、自用分支、仍保留的定制与测试位置。不得声称已执行未发生的提交、回退或测试。
